# `lib/mapping/` — Java → Bedrock mapping data

Milestone **M5** (SPEC §9). Biome and block state tables are both landed;
the biome fallback is not.

This component is deliberately **downstream of the conformance boundary**:
Tier-A parity is diffed in *Java block space* (SPEC §7) before anything is
mapped to Bedrock. Nothing in here may influence generation — it is its own
CMake target, `stratum_mapping`, and `stratum_core` never links it.

Everything here is **platform-neutral Bedrock data**, pinned per Minecraft
version and regenerated by `tools/mapping-sync` when the pin moves. Turning
that data into a specific server platform's own block ids is each native
binding's job (`ext/`, `ext-nukkit/`), through the platform's own resolver.

## Landed: biome mapping

`bedrockBiomeId()` (`include/stratum/mapping/biome.hpp`) maps a Java biome
resource location to Bedrock's numeric id, from a table generated by
`tools/mapping-sync` off GeyserMC/mappings (MIT) at the commit GeyserMC/Geyser
itself shipped for this build's pinned Java version. All 65 vanilla biomes
resolve; `vanilla_biome_mapping_test.cpp` is the fixture-backed full-coverage
check.

One compiled-in table, unversioned by Bedrock protocol, is the right shape
here — checked against the ecosystem's own practice rather than assumed:
Geyser's own biome loader does the same (one `biomes.json`, no per-version
selection; see SPEC.md's M5 entry for the full evidence), because biome id
drift happens at Minecraft-version granularity, which regenerating this
table on a version bump already covers.

**Not yet landed:** the "nearest vanilla Bedrock biome" fallback SPEC §9
wants for custom/datapack biomes. `bedrockBiomeId()` returns nothing for a
biome outside the table rather than guessing at a default — see the
function's own header for why a placeholder default was rejected in favor
of an honest gap.

## Landed: block state mapping

`javaBlockStateId()` and `bedrockBlockState()`
(`include/stratum/mapping/block_state.hpp`) map a Java block state — a
`settings::BlockState`, with omitted properties taking the block's default —
to vanilla's own state id and to a Bedrock blockstate `{name, states,
version}`: the named, typed shape both PocketMine-MP (`BlockStateData`) and
Nukkit (`BlockStateMapping`'s palette key) already take as input. **Never**
the numeric network runtime id: that is a hash-sorted index that shifts
between Bedrock protocol versions, and each platform derives it per
connection in its own networking layer, long after generation.

The table is `tools/mapping-sync`'s output from three sources, each checked
against the others before anything is written: GeyserMC/mappings'
`blocks.nbt` (indexed by vanilla state id), vanilla's own
`reports/blocks.json` (which names those ids, via `tools/fetch-vanilla`), and
GeyserMC/Geyser's Bedrock 1.21.130 block palette (every resolved state must
be in it, tag types included). All 29,671 Java states at 1.21.11 resolve, to
10,491 distinct Bedrock states at blockstate version 1.21.60.33;
`vanilla_block_state_mapping_test.cpp` re-checks every one through the
compiled loader, plus every state vanilla's noise settings can emit.

An unknown block, property or value is a named `BlockMappingError`, never a
guess. Turning a Bedrock state into a platform's own block id — and
deciding what to do when the platform does not have it — is each binding's
job: SPEC §9 has the measured platform coverage (PMMP `stable` has no
powder snow; Nukkit's older palette still holds every terrain state).
