# `lib/mapping/` — Java → Bedrock mapping data

Milestone **M5** (SPEC §9). Biome mapping is landed; block state mapping's
architecture is set but not started.

This component is deliberately **downstream of the conformance boundary**:
Tier-A parity is diffed in *Java block space* (SPEC §7) before anything is
mapped to Bedrock. Nothing in here may influence generation — it is its own
CMake target, `stratum_mapping`, and `stratum_core` never links it.

Everything here is **platform-neutral Bedrock data**, pinned per Minecraft
version and regenerated by `tools/mapping-sync` when the pin moves. Turning
that data into a specific server platform's own block ids is each native
binding's job (`ext/`, `ext-nukkit/`), through the platform's own resolver.

## Landed: biome mapping

`bedrockBiomeId()` (`include/stratum/mapping/biome.hpp`) maps a Java biome
resource location to Bedrock's numeric id, from a table generated by
`tools/mapping-sync` off GeyserMC/mappings (MIT) at a pinned commit. All 65
vanilla biomes at the pinned Minecraft version resolve; see
`tools/mapping-sync`'s own header for the version-gap measurement (GeyserMC
has no branch for exactly this build's pinned Java version) and
`vanilla_biome_mapping_test.cpp` for the fixture-backed full-coverage check.

One compiled-in table, unversioned by Bedrock protocol, is the right shape
here — checked against the ecosystem's own practice rather than assumed:
Geyser's own biome loader does the same (one `biomes.json`, no per-version
selection; see SPEC.md's M5 entry for the full evidence), because biome id
drift happens at Minecraft-version granularity, which regenerating this
table on a version bump already covers.

**Not yet landed:** the "nearest vanilla Bedrock biome" fallback SPEC §9
wants for custom/datapack biomes. `bedrockBiomeId()` returns nothing for a
biome outside the table rather than guessing at a default — see the
function's own header for why a placeholder default was rejected in favor
of an honest gap.

## Planned: block state mapping

Java block state → Bedrock blockstate `{name, states, version}` — the
named, string-keyed shape both PocketMine-MP (`BlockStateData`) and Nukkit
(`BlockStateMapping`'s palette key) already take as input. **Never** the
numeric network runtime id: that is a hash-sorted index that shifts between
Bedrock protocol versions, and each platform derives it per connection in
its own networking layer, long after generation. (An earlier decision moved
this mapping out of here on the assumption that generation needed that
per-protocol id; reading both platforms' source showed it never does — see
SPEC.md §11's "returns to `lib/mapping/`" entry.)

Open before implementing, in order (PROGRESS.md's M5 section tracks them):

- **Version coupling.** Both platforms' upgraders only move a blockstate
  forward. PMMP `stable` is at blockstate version 1.21.60.33 and Nukkit's
  palette at protocol 729 (Bedrock 1.21.30) — both older than the Bedrock
  release matching this build's Java pin. The table's version must be no
  newer than the oldest platform it serves; how much that matters for the
  states terrain generation actually emits is unmeasured.
- **Sourcing.** GeyserMC/mappings' `blocks.nbt` is a sparse diff keyed by
  Java state ordinal, not full states. Resolving it — most likely by
  running `mappings-generator` as a black-box oracle rather than porting its
  logic — is `tools/mapping-sync`'s next job.
